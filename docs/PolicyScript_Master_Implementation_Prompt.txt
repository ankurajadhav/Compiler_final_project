## 4. Define and implement the PolicyScript language

Implement a real domain-specific language rather than a collection of hardcoded examples.

The following policies must compile:

Example 2:

WHEN time BETWEEN 09:00 AND 17:00;

Example 3:

DENY guest TO access server_room

Example 4:

ALLOW faculty TO access lab
WHEN day = Monday OR day = Friday

Example 5:

Example 6:

DENY student TO access computer_lab
WHEN time BETWEEN 12:00 AND 14:00
PRIORITY 10;

Treat these as actual source programs processed by the compiler.

### 4.1 Language grammar and exact type rules

Implement a documented, unambiguous grammar consistent with the presentation. Use a grammar along these lines, adapting token names to the implementation:

```text
program             → rule+
rule                → effect IDENTIFIER TO ACCESS IDENTIFIER condition? priority? SEMICOLON
effect              → ALLOW | DENY
condition           → WHEN expression
expression          → orExpression
orExpression        → andExpression (OR andExpression)*
andExpression       → primaryCondition (AND primaryCondition)*
primaryCondition    → LPAREN expression RPAREN
                    | timeBetween
                    | timeComparison
                    | dayComparison
timeBetween         → TIME_FIELD BETWEEN TIME_LITERAL AND TIME_LITERAL
timeComparison      → TIME_FIELD TIME_COMPARATOR TIME_LITERAL
dayComparison       → DAY_FIELD DAY_COMPARATOR WEEKDAY
priority            → PRIORITY INTEGER
TIME_COMPARATOR     → = | != | < | <= | > | >=
DAY_COMPARATOR      → = | !=
```

The lexer must recognize `TIME_FIELD` for the reserved field name `time`, `DAY_FIELD` for `day`, and weekday values Monday through Sunday. Keywords and field names are recognized case-insensitively. Role and resource identifiers are matched exactly against configuration values; do not silently lowercase or otherwise rewrite configured names. Weekday names are case-insensitive and normalized to one canonical representation.

Use an identifier form such as `[A-Za-z_][A-Za-z0-9_]*` for role/resource names unless the implementation documents another precise rule. Reserve language keywords so they cannot be used as ordinary role/resource identifiers without escaping; escaping is not required in version 1.

The rule order in version 1 is fixed: optional `WHEN` condition first, optional `PRIORITY` clause after it, and then a required semicolon. For example, both a conditionless priority rule and a conditioned priority rule are valid, but `PRIORITY` before `WHEN` is not valid unless the grammar is deliberately extended and documented.

`program → rule+` means at least one rule is required in a compilable source file. Empty or whitespace-only source must produce a clear diagnostic rather than a false success.

Support:
- `ALLOW` and `DENY` effects.
- `TO`, `ACCESS`, `WHEN`, `BETWEEN`, `AND`, `OR`, and `PRIORITY` keywords.
- Parentheses for grouping Boolean conditions.
- Configured role/resource identifiers, including underscores.
- Time literals in exactly `HH:mm` lexical form.
- Weekday values Monday through Sunday.
- The field-appropriate comparison operators defined above.
- Optional numeric priorities and multiple rules in one file.

Define operator precedence as `AND` before `OR`, with parentheses taking precedence over both. Parsing must build the corresponding expression tree; do not evaluate expressions from left to right without respecting precedence.

The `AND` inside `time BETWEEN 09:00 AND 17:00` is the range separator, not a Boolean operator joining two independent conditions. In a recursive-descent parser, parse a `timeBetween` primary by consuming the full `TIME_FIELD BETWEEN TIME_LITERAL AND TIME_LITERAL` sequence before returning to the general Boolean-expression parser. Thus, `time BETWEEN 09:00 AND 17:00 AND day = Monday` means the time range AND the day condition.

The lexer should recognize a syntactically shaped time token such as `25:00`; semantic analysis must then reject the out-of-range value as an invalid time. A malformed shape such as `9:0x` should instead produce a lexical diagnostic. This keeps lexical, syntactic, and semantic responsibilities clear.

Provide a language-reference section in the README. The application must reject syntax outside the documented grammar and must not quietly guess the author's intended meaning.

### 4.2 Condition semantics

Time values use a 24-hour clock and minute precision. The runtime request time is normalized to an integer minute-of-day in the range 0 through 1439.

A condition such as:

```text
WHEN time BETWEEN 09:00 AND 17:00
```

means that the current time is greater than or equal to 09:00 and less than or equal to 17:00. Both endpoints are inclusive.

The condition may be represented in the IR as a typed inclusive time interval or as an equivalent typed expression. Do not lose its type information or rewrite it to raw strings.

Validate time values correctly:
- `00:00`, `09:00`, and `23:59` are valid.
- `25:00` and `12:75` are invalid semantic values.
- Missing digits, malformed literals, or invalid separators are lexical errors.

Only `time` and `day` are condition fields supported in version 1. For `time`, support `=`, `!=`, `<`, `<=`, `>`, and `>=`, in addition to `BETWEEN`. For `day`, support only `=` and `!=`; do not assign an artificial chronological order to weekdays. A day comparison value must be one of Monday, Tuesday, Wednesday, Thursday, Friday, Saturday, or Sunday. Reject unsupported fields and inappropriate operators with semantic diagnostics.

A missing `WHEN` clause means the condition is always true. Evaluate a missing condition accordingly; do not interpret it as false or as an omitted rule.

The presentation identifies a time range whose start is later than its end as unsupported in version 1. Reject it with a clear diagnostic; do not silently reinterpret it as an overnight range. Equal start and end values represent one inclusive minute.

Implement Boolean expressions correctly. Do not simplify expressions across OR branches using identities that are valid only for AND. All evaluation and optimization must use the same typed condition semantics.

## 9. Conflict and redundancy analysis

This is one of the project's principal features. Implement real analysis over the IR and condition structures.

Detect and report the following categories. Use the same typed condition evaluator and rule-resolution semantics as the access engine. Do not detect overlap, conflict, or shadowing by comparing raw policy strings alone.

### A. Duplicate policies

Example:

ALLOW student TO access lab;

ALLOW student TO access lab;

Identify equivalent duplicate rules. Report both rule IDs and explain why one is redundant.

Do not identify rules with meaningfully different conditions or priorities as exact duplicates.

### B. Direct conflicts

Example:

ALLOW student TO access lab;

DENY student TO access lab;

Detect contradictory outcomes for the same role and resource when their conditions overlap.

A conflict report must contain:
- Involved rule IDs.
- Role and resource.
- Conflict category.
- Condition overlap explanation.
- Priorities.
- Effective resolution.
- Recommended corrective action.

### C. Overlapping conditional policies

Example:

ALLOW student TO access computer_lab
WHEN time BETWEEN 09:00 AND 17:00;

DENY student TO access computer_lab
WHEN time BETWEEN 12:00 AND 14:00
PRIORITY 10;

Correctly determine whether both conditions can hold for the same request.

Two different rules with the same role and resource are not automatically conflicting merely because their effects differ. Their applicable conditions must overlap.

Because all supported conditions are Boolean expressions over only `day` and minute-precision `time`, use exact finite-domain predicate evaluation for overlap: evaluate both conditions for each of the seven weekdays and all 1,440 minute values, and report overlap only if a request makes both predicates true. This handles AND, OR, parentheses, equality/inequality, and time comparisons consistently. Return at least one concrete witness request showing the overlap. A lower-priority rule can still participate in an overlap finding, but the report must separately explain which rule wins under the resolution semantics. Cache predicate results or use bit sets if needed for efficiency.

### D. Shadowed and unreachable rules

Detect rules whose presence can never affect the final ALLOW/DENY outcome under the specified rule-resolution semantics. Make the analysis conservative and evidence-based.

Because version 1 has a finite request domain (seven weekdays and 1,440 minute values per day), use exact finite-domain analysis rather than fragile string comparisons or overly simple interval heuristics:

1. For rules with the same role and resource, evaluate their condition predicates over the supported day/time domain to determine whether their conditions overlap.
2. A condition is impossible/unreachable if it matches no valid day/time request.
3. To prove that a rule is decision-shadowed or decision-redundant, compare the resolved ALLOW/DENY result with the rule present and with that rule removed for every day/minute request for its role/resource pair. Label it definitely decision-shadowed only if removing it never changes the decision.
4. If the result changes for at least one request, do not claim that the rule is fully shadowed. Report partial overlap or another less conclusive finding as appropriate.
5. If removal changes only the explanatory winning rule but never the ALLOW/DENY outcome, describe it as decision-redundant and disclose that the explanation/source attribution may change.

Use the same rule-resolution function and typed condition evaluator as the access engine. An implementation may cache predicate results or use bit sets to avoid repeatedly evaluating the same condition.

### E. Impossible conditions

Reject or diagnose unsupported or impossible conditions, including reversed time ranges that cannot be interpreted under version 1, invalid time values, invalid weekdays, unsupported fields, and type-incompatible comparisons. Distinguish syntax/semantic errors from policy-analysis findings.

### F. Clear reporting

Display all issues in a structured table with:
- Rule ID.
- Issue type.
- Severity.
- Explanation.
- Resolution or recommendation.

Distinguish fatal compiler errors from policy-analysis findings. A deterministic conflict may still be evaluated when it has a defined resolution, but it must never be concealed from the user.

## 10. Precise rule-resolution semantics

Implement one shared, deterministic rule-resolution function. The conflict analyzer, shadowing/redundancy analyzer, optimizer verification, and access engine must use this exact function.

For a given access request:

1. Match rules whose role and resource exactly match the request and whose condition evaluates to true. A rule without a `WHEN` clause always matches its condition.
2. If no rule matches, return `DENY` by default. This is an explicit, documented secure-default implementation decision because the presentation does not specify no-match behavior.
3. The highest numeric priority among matching rules wins. An omitted `PRIORITY` value defaults to `0`; explicit `PRIORITY 0` is therefore equivalent to the omitted default for rule resolution.
4. If `ALLOW` and `DENY` rules share the highest priority, `DENY` wins, as specified in the presentation.
5. If several matching rules have the same winning effect and priority, select the earliest source-order rule as the primary explanatory rule. The UI may show the other matching rules as additional context.
6. Rule IDs and source order must remain traceable after optimization. Optimized rules may refer back to their original source rule IDs.

Priorities are non-negative integers in the range supported by the implementation; define and validate the concrete range in the README (preferably `0` through `Integer.MAX_VALUE`). Do not allow overflow, parse failures, or negative values to silently become valid priorities.

The engine must explain decisions, including the selected rule, priority, relevant competing rules, and whether default DENY was applied. Do not implement different precedence rules in different modules.

Example explanation:

```text
Decision: ACCESS DENIED
Role: student
Resource: computer_lab
Day: Monday
Time: 13:00
Winning policy: Rule 6
Reason: The matching DENY policy has a higher priority than the overlapping ALLOW policy.
```

If no rule matches, explicitly state that default DENY was applied. A policy conflict with deterministic resolution is an analysis finding, not automatically a fatal compiler error. Continue to access evaluation only when lexical, syntax, and semantic compilation succeeded; display unresolved or resolved policy conflicts clearly.

## 11. Optimization passes

Implement actual optimization transformations on the typed IR.

### Pass 1: Exact duplicate elimination

Remove duplicate policies only when they are semantically equivalent, including their effect, role, resource, normalized condition truth set, and effective priority. Since omitted priority defaults to `0`, an omitted priority and explicit `PRIORITY 0` have the same resolution semantics. Keep source mapping and report the eliminated rule and the rule retained.

### Pass 2: Condition simplification

Simplify supported expressions when correctness can be established.

Example:

time > 08:00 AND time > 10:00

can be simplified to:

time > 10:00

Respect inclusive and exclusive bounds, types, parentheses, boolean precedence, and OR branches. Do not use string-based simplification or apply an identity outside its valid logical context.

### Pass 3: Unreachable or redundant policy removal

Remove a policy only when the implementation can prove that removing it preserves every ALLOW/DENY decision across the supported request domain. Consider condition overlap, priorities, source-order behavior, and the equal-priority DENY rule. Do not remove a rule merely because another rule has the same role and resource.

If a rule's condition matches no request, it may be removed as unreachable after reporting the reason. If a rule matches some requests but never changes the final ALLOW/DENY result, it may be removed as decision-redundant. Preserve source mapping and explain that the primary displayed winning rule may change after redundant-rule removal.

### Optimization audit

For every pass, record:
- Pass name.
- Number of rules before and after.
- Transformations performed.
- Removed rules and reasons.
- Simplified conditions.
- Warnings or skipped unsafe transformations.

Show the original and optimized policy sets side by side.

### Mandatory optimization correctness gate

Verify every optimization pass separately. For each pass, compare decisions before and after that pass. If equivalence fails, revert that pass, preserve the last verified policy set, report the counterexample, and do not mark the failed transformation as applied. A later pass must never hide an earlier failed transformation.

Version 1 has a finite input domain for conditions: seven weekdays and 1,440 minute values per day. Implement exhaustive decision-equivalence checking for every role/resource pair referenced by any rule in either the original or optimized policy set, for every weekday, and for every minute from `00:00` through `23:59`. Use the same resolver for both versions.

Pairs that are not referenced by a rule in either policy set always produce default DENY in both versions, so they do not need separate enumeration. For each referenced role/resource pair, the checker must compare the actual ALLOW/DENY outcome at all 10,080 day/time combinations. This is an exact check for the documented version 1 condition language, not a sample-based estimate.

If an equivalence check fails:
- Identify a counterexample request (role, resource, day, and time).
- Display the original and transformed decisions.
- Display the relevant source rules when available.
- Mark the optimization pass as failed and revert it.
- Never label the failed or unverified output as a verified optimized policy set.

Show the original and final verified policy sets side by side, including the pass-by-pass audit log. Run the exhaustive checks on a background task so the JavaFX interface remains responsive. Show progress where practical, and handle cancellation or runtime failures without claiming verification succeeded.

## 16. Diagnostics, reliability, and error handling

Build a central diagnostic model containing severity, error code, message, source location, phase, and relevant rule ID when applicable.

Provide actionable messages. For example:

Error [SEM-UNKNOWN-ROLE]: Role 'unknown_role' is not defined in the active configuration. Check the role configuration or correct the policy identifier.

Error [SEM-INVALID-TIME]: '25:00' is not a valid 24-hour time value.

Error [SYN-MISSING-SEMICOLON]: Expected ';' at the end of the policy rule.

Warnings and analysis findings must not be mistaken for fatal syntax or semantic errors.

Do not swallow exceptions, silently skip invalid rules, return success for failed compilation, or leave controls permanently disabled after an error.

Compilation must produce a well-defined result object containing diagnostics, phase outputs, and success/failure information. The result object must distinguish compilation success, analysis findings, optimization verification status, and access-evaluation status instead of collapsing them into one Boolean flag.

Invalid source must not be partially executed as though it were a valid compiled policy set.

## 18. Definition of complete implementation

The project is complete only when all of the following are satisfied:

- The application can be built and launched from the documented instructions.
- Users can load or enter PolicyScript source and compile it.
- The lexer, parser, AST, semantic analyzer, IR generator, conflict analyzer, optimizer, and access engine are real implemented modules.
- Each displayed phase result is generated from the current input.
- Invalid policies produce meaningful diagnostics.
- Configured student, faculty, guest, and additional roles are handled through configuration.
- Conflict detection respects overlapping conditions and rule precedence.
- Optimization applies only transformations that preserve decisions.
- The equivalence checker identifies decision changes rather than allowing unsafe optimization to pass.
- The access engine returns correct, deterministic decisions with explanations.
- The UI responds to real user input and remains usable during longer operations.
- The application includes executable sample policies and reproducible demonstrations.
- JUnit tests have been run, and any failures have been fixed or explicitly disclosed.
- Documentation accurately reflects the actual implementation.
- There are no buttons that merely pretend to work, hardcoded outputs presented as dynamic results, or major placeholder implementations.
